TflOmniDb — Tooling

Three front-ends ship with the library, all net10 only and all thin shells over library code (Scaffolding/, Migration/) so the logic is testable without a UI.

Tool Project Purpose
Entity scaffolder TflOmniDb.Scaffold (CLI) · TflOmniDb.Scaffold.Web (web UI) Reverse-engineer a schema into [DbTable] / [DbColumn] entities
Table migration TflOmniDbMigration Copy a table's structure and/or data between databases, across providers
Benchmarks TflOmniDb.Benchmarks BenchmarkDotNet suite

1. Entity scaffolder

Generates entity classes for SQL Server, Oracle and PostgreSQL. All logic lives in the TflOmniDb library under Scaffolding/; both front-ends call one ScaffoldFacade.

Two acquisition modes

Mode How it works When
Connected (web UI: Direct connection) Opens a live DbConnection, queries catalog views (CatalogSql), maps rows to ColumnSchema You can reach the database
Air-gap (web UI: Script & paste) SchemaScriptEmitter writes a provider SQL script; the DBA runs it on the locked-down server and pastes the pipe-delimited output back; SchemaDumpParser reads it Production databases you cannot connect to

Both converge on one provider-neutral SchemaModel, so the generator is written once. Integration tests assert the connected reader and the dump parser produce byte-identical output. The Oracle script prefixes the SQL*Plus session settings, PostgreSQL uses \pset, and both NULL-guard their concatenation.

CLI — TflOmniDb.Scaffold

Commands: generate · emit-script · list-tables.

# Interactive wizard — run with NO arguments
dotnet run --project TflOmniDb.Scaffold

# Air-gap: emit a script for the DBA, then generate from their pasted output
dotnet run --project TflOmniDb.Scaffold -- emit-script --provider oracle --schema OMNIDB --out dump.oracle.sql
dotnet run --project TflOmniDb.Scaffold -- generate --provider oracle --from-dump dump.txt --out ./Entities --target fx

# Connected
dotnet run --project TflOmniDb.Scaffold -- generate --provider sqlserver `
    --conn env:TFLOMNIDB_SQLSERVER_CONN --schema dbo --out ./Entities --namespace Bank.Entities

The interactive wizard asks for command, provider, source (live connection / dump), schema, all-tables-vs-single, output folder and namespace, offering numbered menus for every enum and Y/N for the flags.

Key options

Option Default Meaning
--provider — sqlserver / oracle / postgres
--conn — Connection string; env:VAR is resolved from the environment
--from-dump — Air-gap input file instead of --conn
--schema — Source schema
--table (all) Single table; omit for whole-schema
--out — Output directory
--namespace TflEntities Generated namespace
--lang csharp csharp / vbnet — VB emits Imports, <DbColumn(...)>, Public Overridable Property … As T? into .vb files
--target net10 net10 (file-scoped namespace, nullable strings) / fx (braced namespace, non-nullable)
--case upper Casing of the DB identifier written into the attribute
--naming upper Casing of the C#/VB class and member names: upper (verbatim), pascal, verbatim
--no-partial (partial on) Classes are partial by default so hand-written members live in a sibling file the generator never overwrites
--no-column-tokens (tokens on) Suppress the nested Cols class (net10 target only)
--sensitive — Mark columns IsSensitive — the catalog cannot infer this
--rowversion-pattern — Mark a column IsRowVersion — likewise
--skip-table-prefix _ CSV of prefixes skipped in whole-schema mode
--include-all-tables — Opt out of the prefix filter

The two naming axes

They are independent, and confusing them causes runtime "table not found" errors:

  • --case controls the database identifier inside the attribute. The DAL always quotes, so this is casing-critical. Default upper is the most portable: Oracle folds unquoted DDL to uppercase and SQL Server is case-insensitive — so create PostgreSQL tables with quoted uppercase names to match.
  • --naming controls the C#/VB identifier, which is cosmetic. Default upper mirrors the DB name verbatim (B_ACCOUNT → class B_ACCOUNT, ACCOUNT_ID → property ACCOUNT_ID); pascal gives ACCOUNT_BALANCE → AccountBalance.

The generated file name is the DB table name (B_ACCOUNT → B_ACCOUNT.cs / .vb), not the PascalCase class.

Generated output

net10 files are self-contained: the // <auto-generated> header turns Roslyn's nullable context off, so the emitter writes #nullable enable (otherwise nullable strings fail with CS8669) plus using System; so DateTime / Guid resolve without the project's ImplicitUsings.

net10 entities also carry a nested public static class Cols of TflOmniDb.Query.Col tokens (B_ACCOUNT.Cols.ACCOUNT_ID, plus a Cols.Table constant) for the SqlQuery composer — the token field name follows --naming, the new Col("…") argument follows --case. On by default; net10 target only (--target fx never emits it — the Fx library has no Col).

Ambiguous reverse mappings resolve by documented heuristic and emit a // note: for the reviewer — e.g. NVARCHAR(MAX) → NClob, Oracle RAW(16) → Binary, NUMBER(1,0) → Boolean, NUMBER(19,4) → Money. Read the notes; they are exactly the decisions a human should confirm.

Config-seeded defaults

An optional appsettings.json "Scaffold" section seeds the interactive path only — the flag-driven CLI is unchanged. Keys: Command, Provider, Source, Tables, Namespace, OutputDir, Language, Target, Casing, Naming, Partial, SkipUnderscoreColumns, SkipUnderscoreTables, Advanced, SkipTablePrefix, EmitColumnTokens, plus a per-provider Connections block keyed SqlServer / Oracle / PostgreSql with ConnectionString (env:VAR supported) and Schema.

The wizard shows the configured value as each prompt's default — Enter accepts it, typing overrides it for that run; the file is never rewritten. A missing file or section means all-null defaults, i.e. the original hard-coded fallbacks. Binding lives in ScaffoldDefaults.FromConfiguration, unit-tested without a database.

Web UI — TflOmniDb.Scaffold.Web

dotnet run --project TflOmniDb.Scaffold.Web    # then open the printed localhost URL

Minimal API + a static page. Bind to localhost — connected mode takes a connection string (nothing is persisted). The Script & paste box is the primary UX. The UI exposes only Provider / Language / Schema / Table; everything else uses the defaults above.

Scaffold:RequireTable in appsettings.json (default true) makes the table name mandatory — single-table generation by default; set it false to allow whole-schema. A single generated file downloads directly; multiple files use per-file or .zip download. The List tables button (CLI: list-tables) enumerates base tables from a live connection or a pasted dump to drive autocomplete on large schemas.

2. Table migration

Copies a single table's structure and/or data from one database to another — possibly across providers (SQL Server → Oracle, say). Logic lives in the library under Migration/; TflOmniDbMigration is a thin interactive shell mirroring the scaffold wizard. It reuses the existing schema reader, reverse type mappers, raw-SQL helpers and bulk-copy path.

dotnet run --project TflOmniDbMigration        # wizard → preview → confirm → copy + verify

Flow

  1. PrepareAsync(request) — reads the source schema, maps columns, emits the CREATE TABLE DDL and counts source rows without writing anything. This powers the dry-run preview (DDL + column mapping + row count + warnings).
  2. Confirm.
  3. ExecuteAsync(request, plan) — applies the destination-exists behaviour, creates the table, bulk-copies the rows, and verifies the destination row count.

RunAsync does both in one call.

MigrationRequest

Field Notes
Source / destination provider + connection + schema + table
What Structure / Data / Both
WhereCriteria (+ params) Subset a big table
ExistsBehaviour Fail / CreateIfMissing / DropAndRecreate / TruncateThenLoad
OracleUppercase Default true

Identity and PK values are preserved — KeepIdentities is forced on, and destination identity columns are emitted GENERATED BY DEFAULT / IDENTITY(1,1).

Supporting types

  • CreateTableEmitter (public) — the general-purpose CREATE TABLE generator: columns, nullability, preserved identity, table-level PK, best-effort DEFAULT translation (DefaultTranslator), dialect quoting, and Oracle identifiers uppercased so OracleBulkCopy can reach the table. v1 does not copy indexes, foreign keys, check constraints or computed columns.
  • MigrationColumn + MigrationColumnFactory — a runtime column with no [DbColumn] entity behind it, built from a TableSchema via the source provider's reverse type mapper. Ambiguous mappings surface as warnings.
  • DataAccess.BulkCopyAsync(schema, table, IReadOnlyList<MigrationColumn>, rows, options) — the non-generic bulk entry point.

Console extras

Prompt defaults come from an optional appsettings.json "Migration" section: Source / Dest legs, each with Provider / Schema / Table and a per-provider Connections block keyed SqlServer / Oracle / PostgreSql (ConnectionString supports env:VAR). A newly typed connection string can be saved back to appsettings.json via ConnectionStringWriter (System.Text.Json, written verbatim so env:NAME stays a reference). The DDL can also be emitted to a .sql file instead of applied.

Coverage: unit-tested without a database (emitter per dialect, column factory, config binder, connection-string writer); a gated SQL Server → Oracle integration test and demo entry #20 TableMigration exercise it live. TflOmniDb.Scaffold is intentionally left untouched by this tool.

3. Benchmarks

TflOmniDb.Benchmarks — a separate console project using BenchmarkDotNet.

Benchmark Measures Needs a DB?
MetadataBenchmarks MetadataReader.For<T>() cold vs warm cache hit No
SqlGenerationBenchmarks SqlGenerator.For(desc) cached lookup; BuildSelectWhere per-call cost (simple + compound predicates); BuildCount No

# List everything
dotnet run --project TflOmniDb.Benchmarks -c Release -- --list flat

# Run everything
dotnet run --project TflOmniDb.Benchmarks -c Release -- --filter '*'

# In-memory only (no database required)
dotnet run --project TflOmniDb.Benchmarks -c Release -- --filter '*Metadata*' '*Generation*'

The DB-backed benchmarks require TFLOMNIDB_SQLSERVER_CONN in the environment; they create their own BenchWidget / BenchBulkWidget tables and tear them down on cleanup. Results land in TflOmniDb.Benchmarks/BenchmarkDotNet.Artifacts/results/ as *-report-github.md and *-report.html.

4. Demo application

Not a tool as such, but the fastest way to see any feature working: TflOmniDb.Demo is a menu-driven console.

It reads appsettings.json under the TflOmniDb section and is multi-provider — a CSV Providers (e.g. "SqlServer,Oracle,PostgreSql") plus a per-provider Connections block (ConnectionString + DefaultSchema). Each connection string resolves env-var-first (TFLOMNIDB_SQLSERVER_CONN / TFLOMNIDB_ORACLE_CONN / TFLOMNIDB_POSTGRES_CONN — the same names the tests use), then the config value.

Every demo runs against each active provider in turn, with a per-demo banner and a demo × provider summary matrix. Set Providers to a single value to scope the run. A provider whose connection is blank or unreachable is skipped (preflight OpenConnectionAsync), not failed. DemoSchema emits provider-correct DDL so the demos are portable; the stored-procedure demo uses each engine's own model (T-SQL / Oracle REF CURSOR / PostgreSQL CALL); and a no-DB "generated-SQL comparison" entry prints the three dialects side by side — the quickest way to see what differs between engines.

Notable entries: #17 ComplexQuery (composer vs raw SQL), #18 RowAccess, #20 TableMigration, #22 Aggregates, #23 CommandTimeout.

Standing rule: every new library feature ships with both a test and a demo entry wired into Program.cs.

02

Architecture at a glance

Staff use TrustBank CBS from a web browser. Every request passes down the same stack of layers, and each layer has one job. Screens never touch the database directly, and business rules never depend on how a screen is drawn.

03

Layers and tiers

Banks often ask whether TrustBank CBS is a three-tier application. The question has two meanings. Layers are how the code is divided. Tiers are how many separate servers it runs on. TrustBank CBS is strictly layered, and runs on two or three server tiers depending on the deployment shape.

  • The layers are real. Business modules contain no web code at all and run without a web server; our tests and tools call them directly. Any code that crosses a layer fails the build.
  • No separate application server, on purpose. That split dates from platforms where the web server could not host business components. .NET 10 hosts both in one process. Adding the split back would put a network hop on every business call and add new timeouts and partial failures, without adding any capability.

04

What happens on every request

Before any business code runs, a central gate makes four checks. If any one fails, the request is refused and the refusal is logged. Nothing is reachable unless it has been explicitly granted, so a missing or unknown permission means denial, never exposure.

06

Boundaries the build enforces

A module reaches another only through that module's published, read-only contract. These rules are checked automatically: 152 architecture checks fail the build if code crosses a boundary. The structure therefore holds as the team and the codebase grow, rather than eroding the way conventional monoliths do.

07

Growing without a rewrite

Today the platform runs as one application on one database, a design called a modular monolith. That keeps every money movement inside a real database transaction and keeps operations simple: one thing to deploy, monitor and back up. Because the module boundaries are enforced, any module can later run as its own host behind the gateway. That move is a configuration change on the same code, and it already runs in our test deployments.

08

Why not microservices

Microservices split a system into separately deployed services, each with its own database. They buy independent deployment and scaling, and the price is the single database transaction across services. In most business software that trade is acceptable. In core banking it is backwards: a posting that touches the account, the ledger and the authorization queue is exactly the operation that must be all-or-nothing, and one bank's volumes do not need the scaling microservices are bought for.

  • We kept what microservices are good for. Most of their value comes from hard boundaries between areas, and TrustBank CBS has those, enforced on every build. Independent deployment is there too, as per-module hosts behind the gateway.
  • The door stays open. Because the boundaries are enforced, moving one module out later is a planned refactor with a known cost, not a rewrite. Valid triggers: a module outgrows one process, independent teams need separate release cycles, or a regulation requires one domain's data to be held separately.

09

Security in depth

Security is part of the structure, not an add-on. Controls are layered from the network inward, so getting past one layer does not get an attacker past the next.

  • Server-side authorization. What a user can open comes from their assigned rights, checked on the server for every request.
  • Tamper-proof record handling. When a list opens a record, the page carries an encrypted token bound to that user's session and that screen, never the record's database id. A token works once, so it cannot be replayed or edited to reach another record.
  • No secrets in code. Connection strings and keys come from protected configuration and are never written to logs.
  • Passwords cannot be recovered. Passwords are stored as salted one-way hashes, so the platform cannot read them back.

10

Maker-checker control

Financial entries follow the four-eyes principle. The person who enters a record cannot authorize it, and nothing takes effect until a second user does. Where a screen carries authorization limits, the checker's limit for that currency is enforced too.

11

Data and databases

One codebase runs on Microsoft SQL Server, Oracle or PostgreSQL, so the platform fits the database investment a bank already has. New business logic is written in C# rather than in database stored procedures, which means it behaves the same on every database. Every query is parameterized, which removes SQL injection as a class of attack.

  • Portable column types. Flags and identifiers use types that bind identically on all three databases, and screen reviews enforce this.
  • Change control. The migration runner has a read-only status check, so a change-advisory board can see exactly what will be applied before it runs.

12

Network zones

Infrastructure reviews usually ask what runs on the web tier and what runs on the application tier. In the multi-host shape, the gateway is the only component that faces users, and it holds no database credentials. The application hosts and the database sit behind it in their own zones.

13

Deployment shapes

The same build deploys four ways. Banks choose by infrastructure standard (Windows/IIS or containers) and by scale (one host, or a gateway in front of per-module hosts). Changing shape later needs no code change.

14

Reports

Existing Crystal Reports layouts carry over unchanged. CBS checks the user's access and gathers the data. A separate viewer renders the layout and never connects to the database: it receives the data through a signed, single-use handoff.

15

Operations and monitoring

The platform writes structured logs out of the box and can emit traces and metrics in the open OpenTelemetry format. That format plugs into the monitoring stack a bank already runs, with no proprietary agent to install.

16

Operator experience

Every screen is built from the same component toolkit, so staff learn the system once and the same control behaves the same way everywhere. That cuts training time and keying errors.

17

Quality engineering

The guarantees in this document are checked by automated tests, in four independent tiers, each catching what the others cannot. Logic migrated from the original system is also compared with it row for row by automated parity tests.

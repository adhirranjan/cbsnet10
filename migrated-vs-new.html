TrustBank CBS — Migrated vs. New

What the .NET 10 migration carried over from the legacy WebForms/VB.NET application, and what is new — architecture, framework, reusable components, technologies, infrastructure and operations.

Scope. This is the cross-cutting inventory: platform, framework, components, technologies, architecture. It is deliberately not a screen-by-screen or procedure-by-procedure ledger — for that see migration-estimate/00-SUMMARY.md (legacy scope counted) and TflCbs.Lab/README.md (the per-procedure conversion archive).

Last verified: 2026-07-30, against the solution source — 36 projects in TflCbsNet10Sol.slnx. Markdown is the source of truth; the .html twin is generated by scripts/render-docs-html.py.

Authority. Where this document and CLAUDE.md disagree, CLAUDE.md wins.

Visual companion: architecture/diagrams/ — the layered architecture (clients → gateway → hosts → screen RCLs → framework → 9 modules → data, with the legacy estate alongside) and a features/technologies/components board. The .svg files paste straight into PowerPoint or Word if you need to present any of the tables below.

How to read this

Every row is tagged with one of three dispositions. The distinction matters commercially: Ported is behaviour we must not change, Rebuilt is where the shape legitimately differs from legacy, and New is capability the bank did not previously have.

Tag Meaning
Ported Legacy behaviour reproduced deliberately faithfully — 1:1, sometimes byte-for-byte. Divergence here is a defect.
Rebuilt Same user-facing capability, re-engineered on new foundations. The shape changed on purpose; the outcome is equivalent or better.
New No legacy counterpart at all. Net addition to the platform.

2. Architecture

The legacy application had no enforced internal architecture: any page could reach any DLL or call any procedure. Two structural decisions replace that, both New, and both compiler-enforced rather than documented-and-hoped-for.

Concern Legacy New Tag
Framework/screen separation none — pages, controls and BLL freely intermixed Horizontal split: TflCbs.Framework references only TflCbs.Abstractions; screens depend on the framework, never the reverse. Arch-tested. See architecture/reusable-boundary.md New
Business-layer structure one compiled BLL + 5,317 procedures Modular monolith: 9 per-domain assemblies, module = bounded domain (never per-service). Complete 2026-07-29; the interim single TflCbsServices assembly was dissolved. See architecture/modular-monolith.md New
Dependency-free foundation — TflCbs.Abstractions: Result/Result<T>, ICbsModule/ICoreCbsModule, the four framework ports, boundary DTOs, and the shared ServiceQuery/DbErrors helpers. No TflCbs.Entities, no TflOmniDb, no ASP.NET New
Cross-module coupling direct calls Published contracts only — TflCbs.Modules.General.Contracts (IScrollService, IProcessBlockCheck); consumers never see General's implementation New
Inversion at the framework boundary — Four ports (IBroadcastSource, IBankVariableSource, IMenuSource, ISessionValidator) implemented by modules, consumed by the framework, with no-op defaults New
Screen packaging .aspx files in folders Per-domain Razor Class Libraries (TflCbs.Modules.<Area>.Web) composed by the host via gated AddApplicationPart Rebuilt
Shared master data duplicated per module TflCbs.Modules.Reference with an explicit admission rule (no domain behaviour and ≥2 consumers) so it cannot become a dumping ground New
Namespace discipline mixed Namespace == assembly, enforced by NamespaceDisciplineTests; zero exceptions remain New
Legacy URL continuity — A DbMigrator script rewrites the screen's a_Menus.NavigateURL from ~/x.aspx to its new MVC route, so the existing menu entry opens the migrated screen. (Until 2026-08-24 an in-memory config map did this, so the legacy app could keep the old rows.) New (in service of Ported behaviour)
Screen navigation model MainMenu.ascx reading rights per page MenuService + server-side menu authorization; the menu is the access-control list Rebuilt

Full project-by-project map: architecture-overview.md.

3. Framework & web plumbing

Legacy cross-cutting behaviour lived in Base.master's per-request pipeline plus copy-pasted code-behind. It is now one library with a two-call setup: AddCbsFramework() + UseCbsFramework().

Capability Legacy New Tag
Cross-cutting request pipeline MasterPages\Base.master code-behind, per page CbsAccessMiddleware — one ordered pipeline Rebuilt
Access control per-page rights checks, fail-open by omission Fail-closed: a route is allowed only if authenticated + module selected + URL in the user's server-side menu. [CbsAccessScreen] binds sub-routes to their owning screen Rebuilt — the policy is new (fail-closed)
Single-session guard IsUserAlreadyLoggedIn in the master page Per-request check via ISessionValidator → AuthenticationService.IsSessionActiveAsync Ported
Financial-year readiness gate master-page check Per-screen gate, opt out via [CbsSkipFinancialYearCheck]; missing FY → login?reason=financialyearnotfound with a visible notice Ported (behaviour) / Rebuilt (mechanism)
CRUD controller scaffolding copy-pasted code-behind CbsScreenController base — TryOpenRecord/TryBeginWrite/TryConsume/ProtectId, SavedOk/UpdatedOk/DeletedOk, TryLoad, EditFailed, RunSearch New
Search backend encrypted SQL shipped in the popup URL SearchEndpoint + SearchRequest/SearchResponse — the server owns the query; only values cross the wire Rebuilt — a security fix, not a port
Primary keys on the client raw PKs in query strings and grid rows RowToken — AES, bound to screen + session, single-use on write New
No-cache on authenticated responses inconsistent Enforced centrally Rebuilt
Provider selection SQL Server, compile-time DatabaseSelector + multi-provider DataAccess wiring; dev-only _DbSwitcher to change provider at runtime New
Health checks none DatabaseHealthCheck + endpoints per host New
Security response headers none UseCbsSecurityHeaders first in the pipeline — CSP, X-Frame-Options, et al. New
Forwarded headers n/a (single site) ForwardedHeaders:Enabled so a host behind the gateway sees the real origin New

11. Deliberately not carried over, and known gaps

Stated plainly so nobody assumes parity where there is none.

Replaced on purpose (do not port back)

  • SQL in the client. Legacy shipped encrypted SQL in popup URLs. Never reintroduced — the server owns the query.
  • Raw primary keys on the client. Replaced by RowToken.
  • Per-page rights checks. Replaced by the fail-closed menu-derived guard.
  • Reversible password storage. Clean break to PBKDF2; every user was reset to a temp password once.
  • ViewState / postback lifecycle. No equivalent; screens are stateless MVC round trips.
  • Session snapshots of bank/branch variables. Replaced by the read-through reference cache (this also removed non-serializable session state).
  • New stored procedures. Prohibited for new master CRUD.
  • Magic-string command dispatch as the only POST model. Now per-action attribute routing; command-dispatch remains where it fits.

Not yet migrated

  • Reports — 399 of the 1,458 legacy screens. No reporting stack chosen yet; the legacy Excel/PDF/DOS-print DLL zoo has no counterpart.
  • The bulk of functional screens — 1,059 counted; roughly a dozen are live in the new host (State, District, Taluka, DiscipActionHistory, LockerType, AccHoldingAmount, Module, Role, Account, Clients, ReferenceCache, ConnectedUsers) plus the shell (Login, Modules, Home/menu, AccessDenied, Error).
  • Core engine procedures — interest, GL, day-end, clearing (~600 pd in the estimate).
  • Login extras — MFA (AD / QR / OTP), RC4 login path, InitSession (see TODO.txt).
  • Oracle gap in TflOmniDb and server-side uppercase normalisation (the current uppercase behaviour is a client convenience only).
  • Data migration + parallel-run tooling.

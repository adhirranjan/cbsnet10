Decisions this plan is built on

Three scoping decisions were made before drafting:

  1. Target = clear the production gate. Fix the Critical + High blockers only; do not chase the Medium tier (observability, distributed session, DB-migration tooling, DIP extraction). Those belong to the "80+" band and are listed at the end as the next program, not this one.
  2. Break bug-for-bug legacy parity where parity is the root cause. Specifically, replace reversible password storage with a real one-way scheme, built on the in-house TflSecurityCrypto library (_Archive\Ad.ProjectLibrary\Tssipl.Security.Cryptography) rather than a new third-party dependency.
  3. This is a plan document. It sequences the work, estimates effort, and defines "done" per item. It makes no code changes.

The gate in one line: eight fixes across four workstreams — an immediate auth-bypass patch, real password hashing, CSRF, secrets externalization, security headers, a guard-ordering assertion, optimistic concurrency, and the source-control/CI safety net that keeps them from regressing. Clear these and the system moves from "fails an audit on day one" to "defensible to deploy."

The reason the overall sits at 62 is that a handful of items act as a hard ceiling: as long as a config flag can bypass authentication and passwords are recoverable, no amount of clean architecture makes the system shippable. Removing the ceiling is what this plan buys.

3. Workstreams & sequence

Four workstreams. The ordering is deliberate: the safety net goes in first so every subsequent fix lands behind a test/secret gate, then the same-day security patches, then the two changes that need care (passwords, concurrency).

Phase 0  Safety net          ── git + CI ──────────────────────────┐  (enables all below)
Phase 1  Same-day security   ── C-1 · H-4 · headers · H-2 secrets ──┤  (small, high-confidence)
Phase 2  Auth hardening      ── C-2 passwords · H-1 CSRF · login RL ─┤  (needs migration care)
Phase 3  Data integrity      ── H-6 optimistic concurrency ─────────┘  (schema + pattern change)

Phase 0 — Source control + CI (H-3) — the prerequisite

  • git init (a correct .gitignore already exists — it excludes .env, certs/, *.pfx, bin/obj). First commit is the current tree after H-2's secret sweep, so no secret ever enters history.
  • Pipeline (GitHub Actions or Azure DevOps): build TflCbs.Entities → build solution → dotnet test TflCbs.Tests + TflCbs.ArchTests → secret scan (gitleaks) → SAST (dotnet analyzers / CodeQL). Red blocks merge.
  • Note on tests: the suite currently needs a live DB and collapses to ~0 cases without one. CI value on day one is the failure-path facts + arch tests + build + scans. A containerized SQL Server service in CI (to make the cross-provider theories run) is a fast-follow, not a gate blocker.
  • Effort: Medium · Risk: low · Done when: a PR with a planted secret or a failing arch test is blocked by CI.

4. The password fix, in detail (C-2)

This is the item the parity decision was about, so it gets its own section — and it needs an honest read of what TflSecurityCrypto gives you today.

Current state

The login compares the submitted password, run through TflSecurityCrypto.Cryptography, against a stored value (AuthenticationService.cs:296-299). The library's usable password path is 3DES-ECB (Encrypt(text, useHashing:true), Cryptography.cs:27) or raw MD5 (Encrypt(text)) — both recoverable/inadequate. A DB compromise yields plaintext.

What the library already offers — and its two gaps

TflSecurityCrypto does ship a salted-hash primitive: Cryptography.Encrypt(text, salt) and Cryptography.VerifyHash(text, salt), backed by SimpleHash.ComputeHash(…, "SHA256", …). Using it would already be a large improvement — one-way and salted instead of reversible. But for a bank it has two real gaps you must not gloss over:

  1. It's single-pass SHA256, not an adaptive hash. No key stretching → fast to brute-force offline on GPUs. The random-salt path also uses only a 4–7 byte salt (SimpleHash.cs:27-32) and a hard-coded pepper ("~!@#$%^&*()_+|") baked into source — a static, non-secret value.
  2. The public VerifyHash(text, salt) can't verify against a stored hash. Its signature takes no stored value; it recomputes a hash from text and compares to itself (Cryptography.cs:129-135) — effectively always true for the same input. It is unusable as-is for login verification.

Recommended: add a proper primitive to TflSecurityCrypto

This honors "use TflSecurityCrypto" while actually fixing the root cause — keep it in the library the team trusts, add no external package, use only in-box .NET crypto:

  • New PasswordHash.Create(password) / PasswordHash.Verify(password, stored) using PBKDF2-HMAC-SHA256 (Rfc2898DeriveBytes, in-box, FIPS-friendly), a 16-byte per-user random salt, ≥100,000 iterations (tune to ~100 ms), and a versioned self-describing format — e.g. v1$iterations$base64(salt)$base64(hash) — so iteration counts can rise over time without breaking stored values.
  • Give Verify a real (password, storedHash) signature that parses the format, re-derives with the embedded salt/iterations, and does a constant-time compare (fixes the != timing side-channel too).
  • (Alternative if the library truly cannot change: PBKDF2 via Rfc2898DeriveBytes directly in AuthenticationService — same crypto, also zero new dependencies. The plain salted-SHA256 helper is the floor, acceptable only as a stopgap with the caveats above stated in writing.)

Migration — no big bang

The login path is a single choke point (AuthenticateUserAsync), which makes a rehash-on-login migration clean:

  1. Add a PASSWORDVERSION (and, cleanest, a new PASSWORDHASH) column to A_USER so old and new coexist.
  2. On login: if the stored value is new-format → PasswordHash.Verify. If legacy → verify with the old scheme; on success, immediately re-hash with PasswordHash.Create and store, stamping the new version.
  3. Users migrate transparently as they log in. Dormant accounts get a forced reset after a cutover window (also closes the "change-password screen is a dead href="#"" gap noted in the review).

Effort: Medium (library primitive Small; schema + dual-read + migration the bulk) · Risk: medium — password paths are sensitive; land behind the CI gate (Phase 0) with unit tests for create/verify/rehash and a golden-vector test proving legacy verification still works during the window.

6. Definition of done (per item)

  • C-1 — a wrong password with MFA_AD_LOGIN_ENABLED (or the QR/OTP flags) set to any value fails — the flag-on-but-no-authenticator path returns Result.Fail, never success; a test pins the invariant (wrong password + flag on ⇒ fails). AD/QR/OTP behavior is decided: on the roadmap, tracked in BACKLOG.md, out of this gate.
  • C-2 — new logins store PBKDF2 versioned hashes; legacy users transparently upgrade on login; no plaintext/reversible value is ever written; unit + golden-vector tests green in CI.
  • H-1 — a forged cross-site POST (Save/Login/Logout) is rejected; the fetch search endpoints send and validate the token.
  • H-2 — no connection string, password, or key in committed config; app runs under a least-privilege SQL login; TrustServerCertificate gone; secret scan clean in CI.
  • H-3 — CI blocks a PR that fails build, tests, arch tests, secret scan, or SAST.
  • H-4 — mis-ordering the middleware fails fast at startup (or the guard stays fail-closed on a null endpoint for a routed path), proven by a test.
  • H-6 — two concurrent edits to the same record produce a clean Result.Fail on the second, not a silent overwrite; X_SCROLL unique constraint confirmed present per provider. (⏳ Reference implementation landed on the State master using TflOmniDb's native row-version — mark the column [DbColumn(IsRowVersion=true)] and the repository auto-increments it, appends the AND VERSION=@expected guard, and throws ConcurrencyException on a stale update; a passing stale-version conflict test on the dev DB proves it. The remaining write services adopt the same pattern — rollout order deferred.)
  • Login rate limiting (M-3) ✅ — credential POSTs beyond the budget answer 429 + Retry-After on every host, not just behind the gateway, and the permitted attempts still reach the pipeline (a limiter that rejected from the first request would satisfy a naive "eventually 429" check while breaking sign-in). Proven by tests that boot the real host: the budget trips, each credential endpoint has its own, Enabled=false leaves login working rather than 500ing, and the pinned limit is asserted to actually reach the framework. Trust prerequisite included: a backend behind the gateway resolves the real client IP (else the partition is one shared bucket); a malformed ForwardedHeaders trust entry fails startup instead of being skipped; and a missing one announces itself — a discarded X-Forwarded-For logs one Security warning per host start, so "the limiter is running but throttling everyone as one client" is visible in the log rather than inferred from a wrong returnUrl.
  • Headers ✅ — response carries a fully strict CSP (script-src/style-src 'self', no nonce, no unsafe-inline) + X-Frame-Options/X-Content-Type-Options/Referrer-Policy/Permissions-Policy on every response incl. static files; the app renders with zero CSP violations (achieved by externalising all inline scripts, moving inline handlers to delegated data-cbs-* listeners, and inline styles to CSS classes — no nonce needed).

7. Risks & watch-items

  • MFA_AD_LOGIN_ENABLED semantics — RESOLVED (2026-07-10). AD (and QR/OTP) login is confirmed on the roadmap, so C-1 does not delete the branch; it makes the path fail-closed until a real authenticator exists, and the login modes become backlog features (§8, BACKLOG.md). Remaining discipline: never let the flag's presence imply a trusted session, and don't ship the AD stub returning success. (This unblocks C-1 and C-2 — both previously waited on this decision.)
  • X_SCROLL unique constraint (blocks part of H-6). The existing MAX+1 duplicate-key retry only works if the DB enforces the unique index. Verify it exists in SQL Server, Oracle, and PostgreSQL targets before relying on it.
  • Password migration window. Legacy verification must keep working until all active users have logged in once. Keep the dual-read path until a measured cutover; force-reset dormant accounts rather than carrying legacy verification forever.
  • CSP breakage — RESOLVED (2026-07-18). Rather than nonce the inline surface, it was removed: 3 inline <script> blocks externalised to .js, 15 inline on*= handlers (incl. _Notification.cshtml) moved to delegated data-cbs-* listeners in site.js, and 32 inline style= attributes moved to CSS classes. The one JSON <script> island is type="application/json" (non-executable — CSP never blocks it), so no nonce was needed. Shipped as a fully strict enforced CSP with zero console violations.
  • Secret rotation. Externalizing secrets (H-2) is also the moment to rotate the exposed sa/sql@2019 credentials — they must be considered compromised since they were in plaintext config.
  • Proxy trust on the IIS farm (open, manual). Several controls silently depend on each backend trusting the gateway's X-Forwarded-For: the M-3 login limiter's per-client partition, b_LoginPolicy.RemoteHostLoginAttempt's per-IP lockout, the same-workstation force-logout, and request attribution in the logs. Untrusted, all of them see one client — the gateway. The Docker stacks now configure this themselves; an IIS farm still sets ForwardedHeaders:KnownProxies by hand per site. Survival across a redeploy depends on where it was put: the documented route (iis-multi-host.md §3) is each site's appsettings.Production.json, which dotnet publish leaves alone (no host project ships that file, and publish doesn't clean the output folder) — but anything placed in web.config <environmentVariables> is wiped, because ANCM regenerates web.config on every publish. deploy-cbs-iis.ps1 prints the reminder and the consequences. Mitigated 2026-07-31 (detection, not enforcement): UseCbsForwardedHeaders now logs one Security-category warning per host start when an X-Forwarded-For arrives and is discarded because the peer isn't trusted — detected by the header still standing with no X-Original-For, the marker the framework middleware writes for what it consumes. Silent when configured correctly and when no proxy exists, so it is a signal rather than noise; it names both the fix and what is silently degraded meanwhile. That converts the whole class from invisible to greppable on every deployment shape. Still not enforced — a host with the wrong trust list serves happily — so the post-deploy check stands: an unauthenticated redirect's returnUrl must carry the gateway origin, not a backend port.

8. Explicitly out of scope (the next band, 80+)

Not part of this gate — listed so the boundary is clear.

Login-mode features (confirmed roadmap — see BACKLOG.md "Authentication & login modes"). The full AD, QR-at-login, and OTP-at-login modes (plus the legacy RC4 login variant) are feature work, not gate items. 2026-07-31 — M-3 (login rate limiting) closed on every host: score ~76.5 → ~77. The ~90-band row "Login-specific rate limiting on all hosts (not just the gateway)" is ✅ done, and as with M-4 the finding was two gaps stated as one. The headline half — nothing on a directly-reached host, so the single-host deployments had no limiter at all — is the obvious one. The quieter half is that the limiter that did exist was volumetric, not credential-specific: 600 requests / 60 s per IP across all traffic allows roughly 600 password guesses a minute, so even the multi-host shape had no working brute-force control, only the appearance of one. Fix: a cbs-login policy registered in AddCbsFramework with UseRateLimiter() inserted first in UseCbsFramework(), ahead of session load, identity-cookie decryption and any DB round-trip — the cheapest point at which an attempt can be refused. The two credential-accepting POSTs opt in with [EnableRateLimiting], and because AccountController lives in TflCbs.Core.Authentication.Web — an application part in all five hosts — one attribute covers every deployment shape instead of five copies that drift apart. Partition is client IP + request path (10 / 60 s by default), so a run against the login form cannot also deny the anonymous change-password screen. Three calls worth recording because each rejects an obvious-looking alternative: the per-username dimension stays with the DB lockout, since partitioning on the posted username requires a synchronous form-body read that Kestrel disables by default; the 429 carries no body, because the middleware owns the status code around OnRejected and writing one risks starting the response first; and Enabled=false still registers the policy as a no-limiter, because an unregistered policy name is a request-time 500 on the login page — a config flag must not be able to break sign-in. A zero or negative size is a startup error, never a silent "off". The prerequisite closed with it, and was the larger piece of work. The partition only means anything if the gateway's X-Forwarded-For is trusted — and compose.multi.yaml shipped with trust commented out, not from neglect but because UseCbsForwardedHeaders read KnownProxies (exact IPs) while a Compose service's IP changes on every up. Untrusted, every backend sees the gateway as the client and three controls collapse together: the limiter throttles the bank as one bucket, RemoteHostLoginAttempt counts all users' failures against one row, and request logs credit the gateway. So the framework gained CIDR KnownNetworks, the plain stack trusts the bridge pool, the HTTPS overlay tightens back to the single static gateway IP, and malformed trust entries now fail startup rather than being skipped — the previous TryParse-and-ignore let a typo read as a trust list that wasn't in force. And because the missing-entry case throws nothing and breaks no page, UseCbsForwardedHeaders also gained a detector: one Security warning per host start when an X-Forwarded-For is discarded as untrusted, identified exactly (the header still standing with no X-Original-For, the marker the framework middleware writes for what it consumed) rather than guessed at. 25 tests in total; seven boot the real host deliberately, because the parser tests would all still pass under a renamed config key or a dropped detector, and the production symptom of either is silence, not a crash. Not claimed: IIS farms still pin KnownProxies by hand (see §7), and the gateway keeps its volumetric limiter as a separate edge layer.

Observability (OTel) — what the +1.5 buys, and the shape of the work. Update (2026-07-18 — instrumentation DONE): the app-side instrumentation described below has since landed as AddCbsObservability (OTel traces + metrics + OTLP exporter + the TflOmniDb DAL ActivitySource + log-trace correlation), wired in all 5 hosts and the gateway, off by default. The rest of this note is the original rationale. Of the three pillars (logs / metrics / traces), only logs were present (TflLog: structured, correlation Reference, categories incl. Performance/Request, per-request middleware). Metrics and traces are missing — no request rate / p95–p99 latency / error rate, and no gateway→host→DB span tree — which is the "blind in production" gap: you learn of problems from user complaints, and there's nothing to alert on. OpenTelemetry is vendor-neutral — instrument once (turnkey auto-instrumentation for ASP.NET Core + HttpClient, and DB spans free for SQL Server via Microsoft.Data.SqlClient and for PostgreSQL via Npgsql's built-in OTel), export to any backend. (Oracle's managed provider emits no OTel spans; and because TflOmniDb is editable in-house source — not a bare DLL — uniform DB spans across all three providers, with the SQL/provider/row-count/correlation-id the DAL already tracks, come from adding a single ActivitySource at the DAL's existing central command seam — one place, not per-call-site.) High-value 80/20: RED metrics (rate/errors/duration per endpoint) + auto-traces, with W3C traceparent propagated across the YARP gateway so a request is a single trace, and the OTel trace-id unified with the existing correlation Reference so a log line links to its trace. The real cost is Infra/ops, not code: standing up and operating the backend — OTel Collector → Prometheus/Tempo + Grafana (self-hosted, for data-residency) or SaaS (App Insights/Datadog) — with retention, dashboards and SLO alerting. Post-gate Medium (the app runs; logs give forensics) — best paired with the Redis stood up for distributed session and with H-3's pipeline. Decision that drives it: self-hosted vs SaaS backend (data-residency + ops capacity).

This is a plan, not an implementation. It changes no code. The two Critical items (C-1, C-2) come first — C-1 as a fail-closed guard (the AD/QR/OTP login modes are decided as roadmap features, tracked in BACKLOG.md, not part of this gate); everything else sequences behind the CI safety net so the fixes can't silently regress.

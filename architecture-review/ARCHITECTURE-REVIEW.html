TrustBank CBS (.NET 10) — Principal-Level Architecture Review

System: TrustBank Core Banking System — strangler-fig migration from ASP.NET WebForms / VB.NET / .NET 4.8 to .NET 10 / C# MVC Solution: TflCbsNet10Sol (26 projects) Review date: 2026-07-10 Reviewer posture: Principal Software Architect / Enterprise Solution Architect — formal pre-production architecture review of a mission-critical, regulated banking system. Method: Full source inspection across all layers (solution structure, framework, services/data, presentation/hosts, security/config, testing/DevOps). Every material finding is anchored to file:line. Headline Critical findings were re-verified directly against source.

One-paragraph verdict. This is, at the code-craft level, one of the cleaner migration codebases you will review: a genuinely well-factored horizontal framework, a disciplined Result-returning service layer with end-to-end async/CancellationToken, real transactions on the money paths that exist, parameterized SQL, no god classes, and an enforced framework⊥screen boundary. It is not production-ready for a bank, and the gap is not craft — it is security hardening, operational maturity, and migration completeness. There is a config-reachable authentication bypass, no CSRF protection on any POST, passwords stored under reversible encryption, production credentials committed to config, no source control, no CI/CD, no metrics/tracing, no DB change management, and no DR/HA posture. Roughly <2% of the ~1,458-screen / ~5,300-proc legacy scope has been migrated — so what exists is best understood as an excellent reference architecture and vertical slice, not a shippable core banking system. Fix the security-critical items before any production exposure; treat the rest as the roadmap the (already strong) foundation was built to carry.

1. Executive Summary

What this is

A staged strangler-fig rewrite. The legacy WebForms/VB app keeps running; screens are peeled off one at a time into a .NET 10 MVC application composed of per-domain Razor Class Libraries over a shared framework and a Result-returning services layer. The team has invested heavily — and effectively — in the scaffolding for scale: a reusable framework, reusable UI components, a modular-monolith module system, four deployment shapes (IIS single/multi, Docker single/multi) fronted by a YARP gateway, and unusually thorough documentation.

The headline

The engineering discipline is high and the architecture decisions are mostly sound. The blockers to production are concentrated and fixable, but several are severe for a banking context:

Rank Blocker Severity
1 Config-reachable authentication bypass — when the MFA_AD_LOGIN_ENABLED bank variable is non-zero, the password check is skipped and no alternative auth runs → any password logs in a valid user Critical

3 No CSRF/antiforgery on any of ~30 POST actions (Login, Logout, all CRUD, dev DB-switch) High

Items 1–4 are explicitly acknowledged in the team's own BACKLOG.md ("Security hardening: antiforgery… lockout… security headers… PII masking") — they are known and deferred, not unknown. That is a governance point as much as a technical one: a banking system cannot go live with these deferred.

2026-07-31 — M-3 closed: login rate limiting on every host, ~76.5 → ~77. The ~90-band row "Login-specific rate limiting on all hosts" is ✅ done, and like M-4 the finding was two gaps reported as one. "Absent on the direct host" is the half everyone reads; the other half is that the gateway's limiter — the one that was present — is volumetric, not credential-specific: 600 requests/60 s per IP over all traffic permits ~600 password guesses a minute, which is no brute-force control at all. So the single-host shapes had nothing, and the multi-host shape had something that wouldn't trip. Fix: a cbs-login policy registered in AddCbsFramework with UseRateLimiter() inserted first inside UseCbsFramework() — ahead of session load, identity-cookie decryption and any DB round-trip, so a throttled attempt is refused at the cheapest possible point. The two credential-accepting POSTs (/Account/Login, /Account/ChangePassword) opt in via [EnableRateLimiting], and because AccountController ships in TflCbs.Core.Authentication.Web — an application part in all five hosts — one attribute covers every deployment shape rather than five copies that can drift. Partition is client IP + request path (a burst on login cannot exhaust change-password's budget), default 10 / 60 s via Security:LoginRateLimit, rejection 429 + Retry-After logged under the Security category. Two deliberate limits, stated rather than papered over: the per-username dimension stays with the DB lockout (MAXIMUMLOGINATTEMPT), because partitioning on the posted username needs a synchronous form-body read that Kestrel disables by default; and there is no response body on the 429, because the middleware owns the status code around OnRejected and writing a body risks starting the response before it is set. Config that is off still registers the policy as a no-limiter — an unregistered policy name is a request-time 500 on the login page, so a flag must not be able to break sign-in — and a zero/negative size is a startup error, never a silent "off". The prerequisite was closed the same day, and it was the more interesting half. The partition is only per-client if the gateway's X-Forwarded-For is trusted, and the Docker multi-host stack shipped with trust commented out — not by oversight but because UseCbsForwardedHeaders read KnownProxies (exact IPs) only, while a Compose service's IP is reassigned on every up. Untrusted, every backend sees the gateway as the client, which collapses three controls at once: the new limiter throttles the whole bank as one bucket, b_LoginPolicy.RemoteHostLoginAttempt counts everyone's failures against one row, and request logs name the gateway as the caller. So the framework gained CIDR KnownNetworks support (feeding KnownIPNetworks — the KnownNetworks property is obsolete in .NET 10), compose.multi.yaml now trusts the bridge pool and compose.multi.https.yaml tightens that back to the single static gateway IP, and a malformed entry in either list now fails the host at startup instead of being silently skipped — the old TryParse-and-ignore left a typo'd address reading as a trust list that wasn't in force, with symptoms pointing elsewhere entirely. Pinned by 25 tests (9 LoginRateLimitTests + 12 ForwardedProxyTrustTests + 4 UntrustedForwardedHeaderWarningTests), seven of which boot the real host on purpose: the parser unit tests would all still pass if the config key were renamed, and the production symptom of that is a silently untrusted gateway, not a crash. One test earns its place for a different reason — the first draft's ConfigureAppConfiguration override never reached the framework's eager config read, so the throttling tests passed against the shipped budget instead of the pinned one; a fixture guard now fails loudly if that recurs. Because the whole failure mode is invisible — nothing throws, every page renders — UseCbsForwardedHeaders also gained a detector: one Security-category warning per host start when an X-Forwarded-For arrives and is discarded as untrusted (the header still standing with no X-Original-For, which is the marker the framework middleware writes for what it consumed). Silent when correct and when no proxy exists, and it names both the fix and what is degraded meanwhile; 4 tests, which need an IStartupFilter to stamp a non-loopback peer because TestServer's null RemoteIpAddress makes ASP.NET skip the trust check entirely. ⬜ Not covered: IIS farms still pin KnownProxies by hand — now detectable rather than silent, but not enforced (deploy-cbs-iis.ps1 prints the reminder and what breaks without it) — and the gateway keeps its volumetric limiter as a separate edge layer.

2026-07-31 — M-4 closed: PII masking now applies on every host, ~76 → ~76.5. The ~90-band row "PII masking shared to thin hosts" is ✅ done, and the finding turned out to be worse than M-4 described. The review recorded it as "masking would not apply on those hosts"; the actual behaviour was more insidious. MaskingOptions defaults Keys to the banking PII/secret list but defaults Patterns to empty, so the four thin hosts were not running unmasked — they were running half-masked: property-name redaction worked, and value-regex redaction (PAN / Aadhaar sitting inside a free-text message) silently did not. Nothing threw, nothing logged, and §3's own strength claim ("recursive PII/secret masking … wired into every host") read as true because the enricher was indeed wired in every host — only its config was not. A config-shaped gap that presents as a working feature is exactly the class of defect a review is supposed to catch, and this one was under-stated. Fix: the block was extracted to a canonical TflCbs.Host.Main/logmasking.json, deleted from appsettings.json so no second copy exists, linked into all four thin hosts (the routecutover.json pattern), and loaded in each Program.cs before ConfigureTflLogging() — from AppContext.BaseDirectory, since a linked file is absent from the content root under dotnet run. Loaded optional: false: a missing file would degrade to half-masked logging with nothing to notice, so the host now refuses to start instead. Each host re-adds AddEnvironmentVariables() afterwards, because AddJsonFile appends a provider and would otherwise shadow TflLog__Masking__* set in compose or an IIS web.config. Held in place by LogMaskingConfigTests (4 facts: the canonical file defines both Keys and non-empty Patterns; every Sdk.Web host that builds a TflOmniLog pipeline ships it, loads it non-optionally before the pipeline, and re-adds the env provider; no host appsettings.json re-declares the section) — verified by mutation, i.e. both regressions were reintroduced and confirmed to fail the suite. The full +0.5 is taken because the fix ships with the build regardless of CI; the guard's value is what H-3 still discounts. Two caveats keep this from being "PII in logs is solved": M-5 (Database:LogParameterValues can log parameter values) is untouched, and nothing asserts end-to-end that a PAN written through a thin host's real log file comes out redacted — the enricher and the config delivery are each tested, their join is not.

2.2 Layering (verified acyclic)

TflOmniLog → TflCbsServices → TflCbs.Framework → TflCbs.Web.Shared → Modules.*.Web → Host.* No module→module references at the project level (enforced by NetArchTest). This is a clean dependency spine.

2.3 Key architectural choices

  • Horizontal split: TflCbs.Framework (reusable web plumbing) ⊥ screen code, compiler-enforced + arch-tested.
  • Modular monolith: business layer sliced into per-domain module folders (General, HR, RetailBanking, Lockers, Clearing, Accounts, Administration) with ICbsModule self-registration and config gating (Modules:Enabled). One process, one DB in steady state — the doc explicitly warns against drifting into microservices.
  • Multi-host as a deployment shape, not a distributed system: the same assemblies can be split behind a gateway for isolation; SSO works via a shared DataProtection key ring + a cross-host auth cookie.
  • Reusable UI components: record picker, account picker, date picker, search modal — vanilla-JS, config-driven, server-side paged.
  • Capability tokens: opaque, DataProtection-encrypted, single-use RowTokens replace raw PKs in the UI.

3. Strengths (what senior architects would praise)

  1. Framework layer is genuinely excellent. 48 files, largest 281 lines, zero god classes, zero utility dumping grounds, all interfaces 1–4 members (ISP respected), no captive dependencies (middlewares method-inject scoped services — the correct pattern), correct async/ConfigureAwait(false) hygiene. This is the strongest part of the codebase.
  2. Services layer discipline. Every public method returns Result/Result<T>; no exceptions cross the boundary; CancellationToken threaded end-to-end; no sync-over-async anywhere; real ExecuteInTransactionAsync unit-of-work wrapping multi-step money/maker-checker operations; parameterized SQL throughout (no injection found in production code).
  3. Fail-closed access model. CbsAccessMiddleware denies by default; unknown menu → /AccessDenied; menu-load error → empty menu; server-side URL-based menu authorization from a HashSet.Contains (0 DB hits per request in the single-host steady state).
  4. Strong client-security defaults. XSS-safe rendering (td.textContent, no user data into innerHTML), overposting defense via hand-written Form DTOs + [Bind(Prefix="Form")] + server-side token-derived PKs, session-fixation handled correctly (session re-mint on login), open-redirect guard on returnUrl.
  5. Production-grade structured logging (TflOmniLog): categories, correlation IDs, recursive PII/secret masking (Password/Pin/Otp/AccountNo/CardNo/Cvv/Pan), buffered async SQL sink that never throws, audit trail with before/after. Wired into every host. (Correction, 2026-07-31: "wired into every host" was true of the enricher but not of its config — the regex half of masking was configured on the default host only, which is finding M-4. The claim is true as written since M-4 was closed; before that it over-stated the control, and the way it over-stated it — a feature that is present, half-configured, and silent about the difference — is worth remembering when reading any other "wired everywhere" claim in this review.)
  6. Mature health-check split: /health (liveness, no dependency checks) vs /health/ready (provider-aware DB probe), wired into all deploy shapes.
  7. Reference cache (IReferenceCache): generation-token O(1) flush, per-key stampede guard, fail-open (never throws, falls back to loader), Redis-optional. Well-engineered.
  8. Documentation is exceptional for a codebase this age: 29 Markdown docs with generated HTML twins, architecture decision records, a costed migration estimate (~10,550 person-days), deployment runbooks with troubleshooting tables. Agent-maintained to stay current.
  9. Modular-monolith boundaries are arch-tested, including a DI-graph resolvability check that turns a missing registration into a test failure — an unusually good control.

4. Weaknesses (ranked)

  1. Security hardening is deferred, not done — auth bypass, reversible passwords, no CSRF, no security headers, no login lockout wired at the MVC layer, committed prod secrets. (§7)
  2. No engineering safety net — not a git repo, no CI/CD, no IaC, no automated test gate; tests need a live DB and hard-code the sa password. (§11, §12)
  3. Concurrency correctness — no optimistic concurrency/rowversion anywhere; read-modify-write lost updates; MAX+1 id generation races mitigated only by a unique-index-dependent retry. (§8)
  4. Scale ceiling in the session model — server-side session lives in single-node IMemoryCache (a TODO in code), so multi-host relies on per-request DB rehydration and cannot horizontally scale a single host without a distributed store. (§6)
  5. In-memory data patterns — pervasive GetAll()-then-filter/sort/page in memory for list screens; on large transactional tables this materializes a full branch table per request. (§8) (Note: the newer generic search endpoint pages at the DB — but only for SQL Server; see §10.)
  6. DIP/build-hygiene leaks — Framework ProjectReferences the concrete TflCbsServices assembly (abstractions not extracted); bare-DLL HintPaths point at Debug binaries in an out-of-solution _Archive path, so no Release closure exists and there's no build-order edge for TflCbs.Entities. (§11)
  7. Observability — ✅ instrumentation done: OpenTelemetry traces + metrics + the TflOmniDb DAL ActivitySource (Oracle-inclusive) + log↔trace correlation, config-gated; gateway→host→DB proven end-to-end. Remaining is the ops half — prod collector topology, curated dashboards, SLO/alerting, logs→Loki. (§12)
  8. Operational maturity — no DB migration tooling (manual DDL), no DR/HA design, sql/ folder nearly empty, node_modules committed under docs/, one stale compose file. (§12)
  9. Anemic domain / primitive obsession — money is raw decimal, accounts are int/string; all logic is transaction-script in services; no aggregates/value objects/domain events. Defensible for a faithful port, but zero domain richness. (§8)

6. Scalability Analysis

Test method: reasoning from architecture + measured per-request cost, not load testing (no load harness exists).

Users (concurrent-ish) Verdict Where it strains
100 ✅ Fine Single host, warm session = 0 DB hits/request for the access guard. Comfortable.
1,000 ✅ Mostly fine In-memory list/filter on large tables (accounts/holds/employees) starts to cost CPU + allocations per search. Reference data re-read per request (no service-layer cache).
10,000 ⚠️ Strains (a) Full-table materialization per search on transactional tables → GC pressure, LOH risk on big result sets. (b) Per-request IsSessionActiveAsync + revocation DB/cache round-trips when auth module wired. (c) Single-node session store becomes a memory-pressure eviction risk → silent session loss + rehydration storms.
100,000 ❌ Fails without rework Single-node IMemoryCache session is the wall. 1,000,000 ❌ Not designed for it Would require: distributed session/cache (Redis), DB read replicas + CQRS read models, DB-side paging on all providers, connection-pool + transient-retry tuning, per-module horizontal scale behind the gateway with affinity, and a caching tier for reference data. The modular-monolith can be scaled per-module behind YARP, but the shared single DB and in-memory patterns are the ceiling.

Bottleneck ranking: (1) single-node session store, (2) load-all-then-filter on large tables (⏳ partial — the account picker's 24 round-trips are now 1 and it is ~2× faster, but the load-all remains and 6 services are untouched), (3) shared single database with no read-replica/CQRS story, (4) per-request auth DB round-trips, (5) no service-layer caching of read-mostly reference data (infra ready — IReferenceCache is distributed + fail-open and proven by BankVars; which masters to cache is a deferred decision, not missing engineering), (6) no transient-fault retry (Polly) so DB blips cascade to user errors (backlogged 2026-07-30; seam settled at the DAL chokepoint, gated on agreeing write-idempotency rules).

Highest-leverage fixes: distributed session (Redis) + gateway session affinity; push filtering/sorting/paging into the DB for the high-volume list screens (provider-dialected); cache reference data via the existing IReferenceCache — infra already built, only the scope decision is outstanding; add Polly transient-retry on DB calls — backlogged, gated on idempotency classification (see BACKLOG.md).

7. Security Analysis

Severity is estimated for a core-banking context. Positive controls are listed too — several are genuinely good and worth preserving.

Critical

  • C-1 — Authentication bypass via MFA_AD_LOGIN_ENABLED. AuthenticationService.cs:299: if (storedPassword != password && mfaAdLoginEnabled == 0). When the MFA_AD_LOGIN_ENABLED bank variable is non-zero, the password mismatch branch never fires, error/isLoginFailed stay unset, and execution falls through to success (line 368+). No AD/alternative authentication is implemented anywhere in the method — the flag gates out the password check without gating in a replacement. Any password authenticates a valid username. Verified directly against source. Fix: never allow the success path when the primary credential is unverified; if AD auth is intended, implement and require it, otherwise remove the flag branch.
  • C-2 — Reversible password storage. AuthenticationService.cs:296-299: submitted password is TflSecurityCrypto.Encrypt-ed and compared as a Latin1 string to a recoverable varbinary. No bcrypt/PBKDF2/Argon2, no per-user salt. A DB compromise = mass plaintext password recovery (and credential-stuffing against other systems). Legacy-parity constraint, but unacceptable at go-live. Fix: migrate to a salted adaptive hash (Argon2id/PBKDF2) with a transparent rehash-on-login upgrade path.

High

  • H-1 — No CSRF protection anywhere. Zero [ValidateAntiForgeryToken] / AutoValidateAntiforgeryToken / AddAntiforgery across ~30 POST actions in 12 controllers (Login, Logout, all Save/Update/Delete/Authorize, the dev DB-switch). Confirmed independently by two review passes. Single-use RowTokens partially mitigate record-scoped writes but do nothing for Save (new record), Login, or Logout. The app emits antiforgery cookies but never validates them. Fix: global AutoValidateAntiforgeryToken + @Html.AntiForgeryToken(); inject the token header on the fetch-based search/JSON endpoints.
  • H-2 — Committed production DB credentials + sa. Base appsettings.json (loaded in all environments) in TflCbs.Host.Main and every TflCbs.Host.* carries User Id=sa;Password=sql@2019;TrustServerCertificate=true. Sysadmin principal, no least-privilege, and TrustServerCertificate=true disables TLS validation to SQL Server (MITM). Fix: move secrets to a secret store / user-secrets / env; use a least-privilege app login; issue a real SQL TLS cert.
  • H-3 — No source control / CI gate (see §12) means none of the above is caught by an automated pipeline before deploy.
  • H-4 — Latent fail-open on middleware ordering. ✅ FIXED (2026-07-18). CbsAccessMiddleware.cs:48: if GetEndpoint() is null the guard passes. If UseCbsFramework() is ever ordered before UseRouting(), every request has a null endpoint → the entire fail-closed guard is silently skipped. Was protected only by a doc comment. Fixed: UseCbsFramework() now calls EnsureEndpointRoutingRegistered() as its first line, throwing at startup if routing hasn't run; pinned by 2 tests (GuardOrderingTests).

Medium

  • M-1 — No security headers: ✅ FIXED (2026-07-18). Was: no CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy — clickjacking + MIME-sniffing exposure on an authenticated banking UI. Fixed: UseCbsSecurityHeaders (framework, first middleware in all 5 hosts) emits all five on every response incl. static files, with a fully strict enforced CSP (script-src/style-src 'self', no nonce, no unsafe-inline); all inline scripts/handlers/styles were refactored out so nothing is exempted.
  • M-2 — Cookie hardening in committed config: auth cookie SecurePolicy=SameAsRequest (can ride HTTP); session cookie sets HttpOnly but not Secure/SameSite. Docker overrides fix it; IIS/other deploys must remember to.
  • M-3 — No login-specific / direct-host rate limiting. ✅ FIXED (2026-07-31). Was: rate limiting existed only on the gateway (600/60s per IP, not login-specific) and was absent entirely on the direct TflCbs.Host.Main host, so brute-force defense relied solely on the DB lockout policy being configured. Fixed: a cbs-login policy registered in AddCbsFramework and applied by UseCbsFramework — so all 5 hosts get it by construction, single-host shapes included — partitioned by client IP + request path, default 10 attempts / 60 s, opted into by the two credential-accepting POSTs (/Account/Login, /Account/ChangePassword) via [EnableRateLimiting]. Rejections are 429 + Retry-After, logged under the Security category, and are refused first in the pipeline — before session load, cookie decryption or any DB round-trip. Config: Security:LoginRateLimit (Enabled=false to disable; a zero/negative value is a startup error, never a silent "off"). Pinned by 9 tests (LoginRateLimitTests, incl. a fixture guard that the pinned limit really reaches the framework). Two limits deliberately kept: the gateway's global limiter stays (volumetric abuse at the edge), and the DB lockout policy stays the per-account control — a middleware limiter cannot partition on the submitted username without a synchronous form-body read, which Kestrel disables by default. Deployment prerequisite — also closed (2026-07-31). The partition key is only the real client IP if ForwardedHeaders is enabled and the gateway is trusted; untrusted, every user shares one partition. The Docker multi-host stack shipped with trust commented out because the framework read KnownProxies (exact IPs) only and a compose service's IP is dynamic. UseCbsForwardedHeaders now also accepts ForwardedHeaders:KnownNetworks (CIDR), compose.multi.yaml trusts the bridge pool (172.16.0.0/12 — safe: only the gateway publishes a port), and compose.multi.https.yaml tightens that back to the single static gateway IP. A malformed entry in either list is now a startup failure rather than being silently skipped. 16 tests (12 ForwardedProxyTrustTests + 4 UntrustedForwardedHeaderWarningTests), 7 of which boot the real host so neither a config-key rename nor a lost detector can pass unnoticed. A missing entry is caught at runtime too: a discarded X-Forwarded-For logs one Security warning per host start. ⬜ IIS farms still set KnownProxies by hand — deploy-cbs-iis.ps1 prints the reminder and the consequences.
  • M-4 — PII masking config missing on thin hosts. ✅ FIXED (2026-07-31). Was: the TflLog Masking block existed in TflCbs.Host.Main but not in the Host.* appsettings. The original wording under-stated it — the effect was not "masking would not apply" but something quieter: MaskingOptions defaults Keys to the banking PII list and defaults Patterns to empty, so the thin hosts ran half-masked — name-based redaction on, value-regex redaction (PAN/Aadhaar in free text) silently off, with nothing thrown or logged to say so. Fixed: the block moved to a canonical logmasking.json (deleted from appsettings.json, so there is no second copy to drift), linked into all four thin hosts like routecutover.json, loaded from AppContext.BaseDirectory before ConfigureTflLogging() and optional: false so a missing file stops the host instead of degrading it, with AddEnvironmentVariables() re-added after (an appended JSON provider would otherwise shadow TflLog__Masking__*). Guarded by LogMaskingConfigTests (4 facts, mutation-verified). Still open in this area: M-5, and no end-to-end assertion that a PAN survives a real thin-host log file redacted.
  • M-5 — Database:LogParameterValues can log SQL parameter values (account numbers, balances, PII) at Information level; gated to Dev by config but the switch exists.
  • M-6 — RouteCutover privilege-escalation surface. ✅ CLOSED (2026-08-24). Was: a misconfigured mapping in routecutover.json pointing a legacy URL at a different screen's route granted that screen's access (AllowedUrls derives from node URLs), with no validation. The legacy WebForms app no longer reads the CBS database, so the whole config layer was deleted — RouteCutover, RouteCutoverOptions, config/routecutover.json and its wiring in all five hosts — and the new route now lives in a_Menus.NavigateURL itself (0004_menu_routes_cutover.sql). MenuService no longer rewrites anything. The surface is not eliminated, it is relocated: a wrong NavigateURL still grants the wrong screen. What changed is that it now takes a reviewed, journalled migration rather than an unvalidated config edit that reloads at runtime, and there is one source of truth instead of two that could disagree. ⬜ Still no validation that a row's route belongs to that row's screen.
  • M-7 — Thin-host Auth:LoginUrl committed as plain HTTP — credentials would 302 to an HTTP origin unless overridden.

Low / Info (positive controls to preserve)

8. Performance Analysis

  • N+1: largely avoided. Related-entity loads are batched with chunked IN lists (Oracle-safe ≤500). Good.
  • Load-all-then-filter/sort/page in memory: pervasive for list screens — GetAllAsync() + in-memory LINQ across ~7+ services (StateService, DistrictService, TalukaService, RoleService, ModuleService, DiscipActionHistoryService, AccountService). On small lookup tables this is fine; on accounts/holds/employees it materializes a full branch table per request → CPU, excessive allocations, and Large Object Heap risk on big pages. The code comments are candid about it.
  • Partially addressed 2026-07-30 — the chattiness, not the load-all. AccountService (the worst case: the account picker) was converted from load-branch-then-rebuild-the-joins-in-memory to one server-side join via the dialected SqlQuery builder. Round-trips per page view fell from 4 + ceil(distinctClients/500) — 24 on the largest branch — to 1, and median latency improved ~2× (330/125/48 ms vs 526/239/70 on 20,480 / 7,516 / 1,392-account branches), overtaking the legacy pr_b_GetAccountList it ports. Verified equivalent on SQL Server and Oracle (identical row Totals). The load-all itself is unchanged — the branch's result set is still materialized per request, so the CPU/allocation/LOH concern in this bullet stands as written, and the remaining six services are untouched. Measurements: docs/perf/AccountList-baseline-2026-07-30.md.
  • In-memory pagination: list.Skip().Take() after full materialization in 8 services; Total = list.Count. Originally noted counterpoint: the generic SearchQueryService paged at the DB with OFFSET/FETCH, but that path was SQL Server-only, so the multi-provider promise broke there. Resolved 2026-07-29 — in the provider direction, not the perf one: SearchQueryService was deleted and its two callers (Locker Type, Disciplinary Action History) converted to Repository<T> + in-memory paging, so no framework code assembles SQL and nothing is provider-specific. The trade was made deliberately: in-memory paging is now universal, so this weakness is broader than when first written — every list screen materializes its (branch-scoped) set. Fine for the lookup masters converted so far; the accounts/holds/employees concern below is unchanged and still the one to fix, now with no DB-paging precedent left in the codebase to build on. Update 2026-07-30 — DB-side paging measured and deliberately deferred. A SqlQuery prototype (4 joins + ORDER BY … OFFSET/FETCH + COUNT(*)) was benchmarked against the account list on the production-scale dev DB and is a regression on 54 of 55 branches: 1.15× faster on the largest branch but 3.6× slower on the median and 11× slower on the small one (715 ms flat vs 196/65 ms). Cause: the paged join full-scans G_GLOBALCLIENT — 166,404 logical reads to return 15 rows — and neither OPTION (RECOMPILE), OPTION (FAST 15), nor paging a derived table first changes it (a forced LOOP JOIN is 6.9 s). The legacy proc escapes it only by embedding literals in dynamic SQL. Also established: paging cannot run on B_ACCOUNT alone — 30 of 1,392 accounts on one branch are dropped by the title join before paging, which is what makes Total correct. So DB-side paging is blocked on a supporting index on B_ACCOUNT(ORGELEMENTID, ACCOUNTSTATUSCODE, ACCOUNTNUMBERFORDISPLAY), not on code. Evidence: docs/perf/AccountList-baseline-2026-07-30.md.
  • No service-layer caching of read-mostly reference data (titles, codes, account heads, modules) — re-read from DB every request despite being pulled fully into memory anyway. Obvious IReferenceCache candidates.
  • Reframed 2026-07-30 — this is a scoping decision, not missing engineering. The infrastructure exists and is production-proven: IReferenceCache is IDistributedCache-backed (in-memory / Redis / SQL Server is a Cache:Provider config choice, not a code change), fail-open by design (a cache fault falls back to the loader, logs, and throws nothing at the caller), with IReferenceCatalog TTLs per category and a /Bank/ReferenceCache inspector + eviction screen. Applying it to a master is wiring: register a category, wrap the existing loader in GetOrCreateAsync, evict on that master's CRUD. Only BankVars (bank/branch variables) consumes it today, and which masters to cache is deferred by decision, not blocked — the measured per-request offenders are catalogued in BACKLOG.md ("Cache-adjacent"): DiscipActionHistoryService (GetAllAsync() over all of G_TITLE + G_DESIGNATION per list render), SearchAccountHeadsAsync (all 1,695 G_ACCOUNTHEAD rows), LockerTypeService/GeneralGrp11Service (B_CODE). The account list's titles/codes/heads no longer qualify — they became a server-side join on 2026-07-30.
  • No transient-fault handling (Polly/retry/circuit-breaker) on any DB call — a transient SQL/Oracle blip surfaces directly as a user error. Material for Azure SQL / networked DBs.
  • Confirmed still absent and formally backlogged 2026-07-30 (no Polly package in Directory.Packages.props, no retry on any DB path) — see BACKLOG.md → "Resilience — transient-fault handling (Polly)". The implementation seam is settled: one policy at TflOmniDb's single execution chokepoint CommandLogger.ExecuteAsync, the same place BindByName and the OTel ActivitySource already live, so every provider and call site inherits it. The open work is idempotency classification, not wiring — in a core banking system a blindly-retried write can double-post, so the policy needs a transient error-code allowlist, free retry on reads, and writes only where the failure provably preceded commit. Deferred until that classification is agreed.
  • Concurrency / lost updates (High). No rowversion/optimistic concurrency token anywhere. The standard update pattern (load full row → mutate → UpdateAsync rewrites every column) is last-writer-wins with silent lost updates under concurrent editors. ScrollService.CreateAsync MAX+1 numbering has an acknowledged duplicate-key race mitigated by a unique-index-dependent 3× retry — verify that unique constraint exists in every target DB, or the retry cannot fire.
  • Async: excellent. No sync-over-async in services or hot framework paths (the only .GetAwaiter().GetResult() is in the DataProtection XML repo — a synchronous ASP.NET contract, startup-only, documented). No async void.
  • The real money path is not yet migrated. AccountService.GetWithdrawableAmountAsync is a stub; the transaction engine lives only in the excluded Lab project. So transaction/concurrency guarantees are proven on holds/CRUD but unproven on the highest-risk balance-movement path.

17. Final Recommendations

  1. Treat this as a foundation, not a product. The architecture is a well-built chassis. Do not let its polish mask that <2% of the banking surface is migrated and the highest-risk money-movement path is still in the excluded Lab project.
  2. Close the four security blockers first (C-1, C-2, H-1, H-2) — they are small-to-medium effort and non-negotiable for a bank. C-1 (auth bypass) is a same-day fix and should be done immediately.
  3. Stand up the engineering safety net now, not later — git + CI (build/test/secret-scan/SAST) will catch the next C-1 before it ships. Its current absence is the single biggest process risk.
  4. Solve concurrency and horizontal scale before load, not after — add rowversion concurrency checks and move session to a distributed store with gateway affinity; both are architecture-shaping and cheaper now than post-launch.
  5. Add the observability and DB-migration pillars — OpenTelemetry ✅ (instrumentation done — traces/metrics/DAL spans/correlation, gateway→host→DB proven; prod backend/dashboards remain) + a versioned migration tool (still to do) are prerequisites for operating a regulated system, independent of feature progress.
  6. Preserve what's good. The framework, Result pattern, module system, reusable components, logging library, and documentation are genuine assets — the roadmap above hardens them; it does not replace them.
  7. Right-size the multi-provider investment. If SQL Server is the only production target, the Oracle/PG DAL and per-method perf harnesses are cost without payoff. Decide explicitly. (Updated 2026-07-29: the original "and the SQL-Server-only search paging already breaks the promise" caveat is gone — that path was removed, so the multi-provider claim is now consistent end-to-end. The decision is a cost/benefit one, not a "the promise is already broken" one.)

Bottom line: Excellent craft on an incomplete, not-yet-secure system. Fix the concentrated Critical/High items, add the missing operational pillars, and this becomes a genuinely strong enterprise platform. Ship it as-is and it fails an audit on day one.
